# 自然写作与干净正文

本规则适用于所有读者可见的最终 Markdown。目标是让正文像经过人工编辑的成稿，而不是模型的检查报告、工作流日志或模板填空。

## 1. 正文与审校信息分开

- 正文只保留读者需要的内容、必要的原文定位以及最终采用的图表。
- 工作流状态、用户选择、来源映射、判断主体、冲突、未决问题和强制通过记录放入配套审校文件。
- 公众号模式使用 `sources.md`、`qa-report.md` 和 `README_BEFORE_PUBLISHING.md` 承载这些信息。
- 论文解读模式另行生成 `<论文PDF文件名去除扩展名>_编辑核查记录.md`。
- 编辑核查记录使用用户选择的语言；严格中英文模式下同样提供平行中英文，选择“其他”时按已确认的单双语方式处理。
- 为自动检查所必需的来源、语言、图注和固定结尾 HTML 注释可以保留，但不得显示为可见正文；较长的编辑说明不得塞入正文注释，应写入审校文件。

正文不得出现以下工作流口吻或把它们当作标题、标签和段首提示：

- “研究级解读”“已确认事项”“待确认”“核验状态”；
- “作者陈述”“证据直接支持”“作者解释”“分析者评价”；
- `PASS`、`WARN`、`BLOCK`、`NEEDS_REVIEW`、`USER_CONFIRMED`、`USER_OVERRIDE`、`user-confirmed-add` 等机器状态；
- “根据 Prompt 要求”“按照 Skill 第几节”“我之所以这样写”“下面将分为”等自我说明。

原始材料确实使用某个词时可以正常引用。例如会议通知中的“已确认嘉宾”是事实表述，不属于工作流状态。

## 2. 自然交代判断归属

内部仍须区分作者主张、论文证据、作者解释和编辑判断，但正文通过具体主语和证据动词自然说明：

- “作者在 Proposition 3 中提出……”
- “Figure 4 显示……”
- “作者把这一结果解释为……”
- “把 Proposition 3 与 Figure 4 放在一起看，两者并不完全一致。更稳妥的理解是……”

不要写成：

- “【作者陈述】……”
- “【证据直接支持】……”
- “【分析者评价】……”

移除标签不等于弱化证据边界。只要一句话含有编辑推断，就要紧接着说明依据；无法确认的内容用自然句子写清楚，例如“论文没有报告这一数值”或“现有图表不足以判断这一点”。详细归属和核验状态写入编辑核查记录。

## 3. 连贯结构

- 按材料或论文的论证顺序推进，让问题、方法、证据和结论自然衔接。
- 论文解读默认只用 4—6 个二级标题，通常不用三级标题。一个小节只有一小段时，优先与相邻内容合并。
- 标题要贴合具体内容，不机械复制“研究问题”“理论机制”“分析者评价”“未来展望”等固定标签。
- 图、表和公式放在它们真正参与论证的位置解释，不另建包含所有图表的清单式章节。
- 段落之间使用事实或逻辑过渡，不连续堆叠项目符号、粗体短语和“标签＋冒号”的句式。

## 4. 重点与篇幅

论文解读不是逐节复述。只选择理解以下内容所必需的信息：

- 论文真正提出的问题；
- 作者如何回答；
- 会改变结论的主要证据；
- 论文新增的认识；
- 最重要的证据边界。

不罗列所有稳健性检验、异质性结果、附录和图表。只有它们会加强、削弱或改变核心结论时才写入正文，其余记录在编辑核查文件。

中文论文解读默认约 3,000—5,000 个中文字符，复杂论文通常不超过约 6,000 个中文字符；超过这一范围前先征得用户同意。原文较短时可以更短，不为满足字数注水。英文、严格中英文或其他语言按相同信息密度和阅读负担控制，而不是机械换算字符数。

公众号稿件继续遵守 `references/editorial-depth-and-footer.md` 的栏目深度要求，但也不得靠重复、空泛展望或过度分节凑篇幅。

## 5. 人类表达审校

交付前通读一次，只处理表达，不改变事实：

- 删除铺垫、规则说明、重复总结和没有信息量的过渡句；
- 避免“此外”“值得注意的是”“不仅……而且……”等机械连接连续出现；
- 避免三项式排比、过多破折号、过度粗体、宣传性词语和整齐得不自然的句式；
- 长短句自然交替，段落围绕一个完整意思展开，不把连续论证切成碎片；
- 使用具体名词、动作、数据和原文位置，少用“重要意义”“深刻影响”“复杂格局”等空泛判断；
- 保持科学、克制和准确，不为显得“像人”而加入随意口吻、无来源观点或虚构个性。

最终正文应当可以直接阅读或进入排版环节。读者不需要知道它经过了哪些 Prompt、Skill、审核状态或交互步骤。
